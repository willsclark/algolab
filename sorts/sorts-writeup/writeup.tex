\begin{abstract}
	This report analyzes the empirical running times of insertion sort, several variations of shell sort, Tim-sort, and skip-list sort with their theoretical complexity. Each algorithm is measured across three input distributions, namely: uniformly distributed, nearly-sorted, and two-alternating. Finally, I declare a best algorithm.
\end{abstract}

\section{Introduction}
Sorting algorithms are the \emph{foundation} of computer science. As per Donald Knuth, "virtually every important aspect of programming arises somewhere in the context of sorting or searching!" And not only that, the speed at which we can sort data is often the limiting factor in modern advancements.
When discussing the "speed" of an algorithm, a natural crossroads appears: \emph{theoretical} speed, or \emph{practical} speed. This report seeks to derive insights from theoretical explanations, and apply them to empirical results. The canonical choice for analysis is \emph{time vs. input size}, but I'd like to append \emph{comparison count vs. input size} to our analysis. Both cases are plotted on log-log scales to make spotting power-law ($T(n) = cn^k$) running times easier. The below algorithms -- and theoretical (worst-case) running times -- are listed for reference later.

\section{Setup}

\subsection{Input Distributions}
A \texttt{Permutation} class was created to handle all input
distributions. Each \texttt{Permutation} instance stores a
\texttt{random.Random(SEED)} into \texttt{self.\_rng}.
\texttt{Permutation} has member functions \texttt{uniform}, \texttt{two\_alt},
and \texttt{almost\_sorted}, yielding a uniformly distributed sequence,
almost sorted sequence (bounded by $\log_2(|S|)$ swaps), and a
two-alternating sequence ($1, 3, 5, \dots, n-1, 2, 4, 6, \dots, n$),
respectively. Since Python implements the Mersenne Twister for its random
number generation, we don't have to worry about any LCG-adjacent issues.

\subsection{Data Collection}
I used \texttt{Pydantic} to store comparisons and time per iteration for every algorithm into \texttt{JSON}.
Pydantic gave me more flexibility than the suggested \texttt{csv} file in the notes. I tested each of the algorithms for $30$ trials, on input sizes $16, 32, 64, 128..., 16384$ as to align them with a $\log_2$ axis when graphing.

\subsection{Graphing}

Using the \texttt{JSON} data, I generated log-log plots for \emph{Comparisons vs. Input Size}, and \emph{Time(s) vs. Input Size} using \texttt{Matplotlib.pyplot}. Each plot has three best fit lines, one for each input distribution. To avoid cluttering, I am only including the \emph{Time(s) vs. Input Size} plots, but will reference the other graphs if needed.

\section{Insertion Sort}
\begin{figure}[ht]
	\centering
	\includegraphics[width=0.6\textwidth]{plots/is_time}
	\caption{Insertion Sort}
	\label{fig:is_time}
\end{figure}
Take $c$ to be the coefficient in front of $\log N$. Insertion sort performed the worst on the uniform distribution ($c = 2.0195$), closely followed by the two-alternating sequence ($ c = 1.9956$), then further away by the near-sorted list ($c = 1.2174$). This directly follows from the theory: our empirical running time for uniform and two-alternating is close to $\mcO (n + k)\subseteq \mcO(n^2)$, but when the list is almost sorted we have close to linear, $\mcO(n)$ run-time, since we don't have to "make room" when fixing an inversion, $k$. When the input is two-alternating, insertion sort scans halfway up the list (until it reaches $S_{n-1}$), then has to do $\mcO(n^2)$ work moving over the odd numbers to insert the even ones. As such, this suggests that insertion sort \emph{is} a viable sort on nearly-sorted sequences, less viable on two-alternating, and should be feared for uniformly distributed inputs.

In all of the shell-sort variations, the \textbf{nearly-sorted input took the least time}, boasting values of $c = 1.2015, 1.1899, 1.1956, 1.2614, 1.1843$ for each variant, respectively. \textbf{A003462} was the \textbf{best among all variants for nearly sorted and two-alternating} inputs. \textbf{Hibbard} was the \textbf{best for uniform} inputs. Here's where things get strange, Shell's original formulation has empirical time complexity for uniform, nearly sorted, and two alternating of $\mcO_{emp}(n^{1.4102}),  \mcO_{emp}(n^{1.2015}), \mcO_{emp}(n^{1.2079})$, which is much less than its theoretical $\mcO(n^2)$ bound. This allows me to conclude that on the average case, Shell-sort is quite an efficient sort. Another observation is that A003586 is almost \emph{input-agnostic}, in the sense that each input produces the same, consistent $\mcO(n^{\approx 1.26})$ time bound. Since the 3-smooth gaps $\{2^a \cdot 3^b\}$ are dense across all scales, no input permutation can consistently evade early reduction passes, yielding stable $\mcO(n^{\approx 1.26})$ regardless of input structure.

The literature tells us that Tim Sort runs in $\mcO(n + n\mcH)\subseteq \mcO(n\log n)$ where $\mcH$ is the Shannon entropy, but upon a naive glance at the runtime of Tim Sort on the \emph{Time vs. Input Size} plot, we get empirical time complexity of $\mcO_{emp}(n^{1.1296})$, $ \mcO_{emp}(n^{0.9711})$ , and $\mcO_{emp}(n^{0.9576})$. It's impossible for a sort to be \emph{this} good, so looking at the comparisons plot, we get: $\mcO_{emp}(n^{1.2373})$, $\mcO_{emp}(n^{1.0968})$, and $ \mcO_{emp}(n^{1.0067})$. Tim Sort almost runs in $\mcO(n)$ in the nearly sorted and two-alternating cases. I conjecture that this is because we only have 2 \textit{monotonic non-decreasing} runs in the two-alternating case (the odd half $1, 3, \dots, n-1$ followed by the even half $2, 4, \dots, n$), so we are effectively only doing \textbf{ONE} merge. It's not quite as extreme in the near-sorted case, but the same logic applies: nearly sorted $\rightarrow$ less runs. On log-log plots, it's quite hard to distinguish between linear and logarithmic functions, but since the exponent, $c \in [1, 1.24]$, it's reasonable to assume an $\mcO(n \log n)$ average case runtime, but if the input is advantageous, \textbf{Tim sort is incredible.}

Skip sort performs incredibly well on all input distributions, validating its "adaptive-sort" classification. The theory tells us that Skip sort has a complexity of $\mcO(n \log n)$ \emph{with high probability}. It's not deterministic since for each input element we repeat \emph{Bernoulli($\frac{1}{2}$)} until we get $0$, which could be infinite if you're (extremely) unlucky. As a general trend, note the $\approx .15$ increase between plots (a) and (b). Since skip sort performs \texttt{insert(x)} (and thus \texttt{search(x)}) for each element, there is some comparison overhead in actually constructing the skip list that is not reflected in runtime.

Let us now compare skip sort to the rest of the algorithms on each input distribution. For \textbf{uniform}, skip sort outperforms every sort except for Tim sort, and by similar reasoning as \emph{Section 5}, we can assume an $\mcO(n \log n)$ run time, which is strictly less than Tim Sort. For \textbf{Almost Sorted}, we only lose to Tim sort in for runtime complexity, but for comparisons we fall middle of the pack. For \textbf{Two-Alternating}, we fall right behind Tim Sort but beat everyone else.

\section{Input Distribution Sensitivity}
% 15 points. Which algorithms are sensitive to input distribution, and which
% are roughly distribution-invariant? Tie observations back to the plots.
To address sensitivity, I split the algorithms into two camps: \emph{input-sensitive} (whose empirical exponent $c$ varies meaningfully across distributions) and \emph{input-agnostic} (whose $c$ is roughly constant). I use the spread $\Delta c = c_{\max} - c_{\min}$ across the three distributions as a rough proxy.

\textbf{Input-sensitive algorithms.} Insertion sort is the most dramatic case, with $\Delta c \approx 0.80$ ($c_{\text{unif}} = 2.02$, $c_{\text{near}} = 1.22$, $c_{\text{two-alt}} = 2.00$). This is expected: insertion sort's running time is governed by the inversion count $k$, which collapses to $\mcO(n)$ on nearly-sorted input but blows up to $\Theta(n^2)$ on uniform and two-alternating sequences. Tim sort is also clearly sensitive ($\Delta c \approx 0.23$ in comparisons), since its merge structure exploits existing runs -- the two-alternating case degenerates to essentially a single merge, and the nearly-sorted case has few long runs to combine. Skip-list sort shows mild sensitivity ($\Delta c \approx 0.07$ in time), which is consistent with its $\mcO(n \log n)$ expected-time guarantee being only weakly dependent on input order.

\textbf{Input-agnostic algorithms.} Among the Shellsort variants, A003586 (Figure \ref{fig:shell4}) is the standout, with all three exponents collapsing to $c \approx 1.26$ ($\Delta c < 0.01$). As argued in Section 4, the density of 3-smooth integers $\{2^a 3^b\}$ across all scales prevents any input permutation from systematically evading early reduction passes. The other Shellsort variants (Shell's original, Hibbard, A083318, A003462) sit in between: their nearly-sorted exponents are noticeably lower ($\approx 1.19$) than uniform ($\approx 1.40$ for Shell's original, $\approx 1.26$ for the others), but the gap is much smaller than insertion sort's.

In summary, sensitivity tracks the algorithm's ability to exploit existing order. Insertion sort and Tim sort are the most adaptive (and thus most sensitive); A003586 Shellsort is the least adaptive (and thus most agnostic); skip-list sort sits in the middle, gaining little from structure but losing little to the lack of it.

\textbf{Tim Sort} is the best algorithm we studied, since it adapts to the input distribution's structure and runs incredibly fast. From a philosophical standpoint, there \textbf{cannot} be any "best" sorting algorithm, since the context in which you'd use a specific sort is non-static. Also, upon a simple Google search, Powersort replaced Tim Sort in \texttt{Python 3.11}, so even in its general domain, Tim-Sort is not the best.
